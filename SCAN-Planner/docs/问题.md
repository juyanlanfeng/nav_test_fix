```cpp
  /**
   * @brief 为下一次规划填写起始位置、速度与加速度。
   * @details 无形参；位置始终用实际里程计。默认速度用里程计、加速度为零；
   *          若当前轨迹存在且时间在允许范围内，则改用轨迹导数以保持参考连续性。
   *          使用轨迹导数时，若水平速度背离目标，会将起始速度和加速度清零。
   * @return 无（void）；输出保存在 start_pt_、start_vel_、start_acc_。
   */
  void SCANReplanFSM::setStartStateFromOdomOrCurrentTraj()
  {
    // 设置起始位置、速度、加速度：直接来自里程计
    start_pt_ = odom_pos_;
    start_vel_ = odom_vel_;
    start_acc_.setZero();

    // 下面这些是检查局部轨迹是否存在
    // 如果存在，则从"当前正在执行的计划"里，取出此刻的速度和加速度，作为下一次规划的起点条件
    // 如果不存在，则直接将里程计数据作为下一次规划的起点条件
    LocalTrajData *info = &planner_manager_->local_data_; // local_data_是规划好的局部轨迹
    if (info->start_time_.seconds() < 1e-5 || info->duration_ <= 1e-5)
      return; // start_time为0或轨迹长度为0->路径不存在

    const double raw_t_cur = (node_->now() - info->start_time_).seconds();
    if (raw_t_cur < -1e-3 || raw_t_cur > info->duration_ + 0.2)
      return; // 路径已经执行的时长，raw_t_cur，其范围应当是[0, duration_]，越界说明有问题，return

    const double t_cur = std::min(std::max(raw_t_cur, 0.0), info->duration_); // 将执行时长raw_t_cur强制约束在[0, duration_]，获得t_cur
    start_vel_ = info->velocity_traj_.evaluateDeBoorT(t_cur); // 从velocity_traj_函数中取出t_cur时刻的数值 
    start_acc_ = info->acceleration_traj_.evaluateDeBoorT(t_cur); // 从acceleration_traj_函数中取出t_cur时刻的数值

    const Eigen::Vector2d to_goal = end_pt_.head<2>() - odom_pos_.head<2>();
    if (to_goal.norm() > 1e-3 && start_vel_.head<2>().dot(to_goal) < 0.0)
    {
      start_vel_.setZero();
      start_acc_.setZero();
    }
  }
```

这里只要局部路径存在，就直接将路径上的理论值作为下一次规划的起始值，但是机器人实际执行的路径跟理论路径显然不可能一样，但是这里还是直接用规划值作计算，误差不是会越来越大吗，为什么不直接用真实的里程计数据作为起始条件规划

这样直接用理论速度规划在机器人上坡或者其他导致实际速度与规划速度不符合的情况时是否会导致规划错误，闭环控制器是否足够纠正这些错误

# 源码核查回答（2026-09-19）

以下结论针对当前本地源码，不推广到原作者其他版本。区分“代码事实”“据此推断的风险”和“建议修法”。本轮只补充回答，没有修改算法，也没有运行仿真。函数名比行号更稳定，后续添加注释会使原问题里的行号移动。

## 回答 1：为什么用参考速度，会不会误差越来越大？

### 1.1 实际上是混合起始状态

在 [scan_replan_fsm.cpp](../src/planner/plan_manage/src/scan_replan_fsm.cpp) 的 `setStartStateFromOdomOrCurrentTraj()` 中：

| 起始量 | 默认来源 | 当前轨迹通过时间检查后 |
| --- | --- | --- |
| `start_pt_` | 里程计位置 | 仍是里程计位置 |
| `start_vel_` | 里程计速度 | 改用参考轨迹的一阶导数 |
| `start_acc_` | 零 | 改用参考轨迹的二阶导数 |

所以不是完整地用理论状态替代真实状态。每次调用仍将位置拉回实际里程计位置，不能直接推出位置误差必然无限积累。

“只要路径存在就使用”也需要细化：起始时间须不小于 `1e-5 s`，轨迹**时长**须大于 `1e-5 s`，当前相对时间须位于 `[-0.001, duration + 0.2] s`，随后被截到 `[0, duration]`。`duration_` 不是空间路径长度。这些条件只检查轨迹时间，没有检查参考速度与真实速度之差。

末尾点积检查使用的也是参考速度：若它在水平面上背离终点方向，就将起始速度和加速度置零。它不能证明机器人已经静止，也不能严格证明机器人实际正在背离目标。

### 1.2 为什么这样写？

从“沿用上一条轨迹导数”的行为看，其作用是保持新旧参考运动的速度、加速度衔接，并减少对测量速度噪声的依赖。这是根据实现做出的解释，不是作者已经给出的稳定性证明。

它牺牲的是起始条件与真实运动的一致性。因为起点位置来自测量，速度/加速度来自参考，这也不是完整的位置、速度、加速度连续拼接。

例如真实坡上速度为 `0.1 m/s`，参考速度为 `0.6 m/s`，下一次规划仍可能以 `0.6 m/s` 为起始速度。结果可能数学上满足轨迹限制，却不符合车辆此刻能实现的运动状态。反过来，真实速度高于参考时，用参考估算停止过程也可能过于乐观。具体是否碰撞或发散需要运行验证，源码本身不能保证。

另一个必须同时处理的位置是 **`planFromCurrentTraj()`**：它同样使用真实位置和参考导数，而且没有调用上述起始状态选择函数，只将轨迹相对时间截到有效区间。只改 `setStartStateFromOdomOrCurrentTraj()` 会遗漏正常重规划路径。

### 1.3 现有闭环控制器是否足够纠正？

[closed_loop_controller.cpp](../src/planner/plan_manage/src/closed_loop_controller.cpp) 的 `cmdCallback()` 实际执行：

```text
世界系平面速度 = 参考平面速度 + kp_pos × 平面位置误差
              → 模长限制 → 按实际 yaw 转车体系 → vx/vy 分别限幅
角速度 = kp_yaw × yaw 误差，再限幅
```

它有位置反馈，因此小的跟踪偏差可能被纠正；但从代码不能认定足以补偿坡道、打滑或严重执行不足：

- `odomCallback()` 只保存位置和 yaw，没有用实测速度建立速度误差反馈。
- 不做坡度动力学补偿，也没有位置 Z 的执行控制。
- 朝向误差过大时冻结轨迹计时；平移严重落后时没有相应的误差阈值冻结/故障处理。
- 限幅可能让纠偏需求无法执行；本函数没有显式的输出加速度限制。
- 只记录“收到过里程计”，不检查其新鲜度。
- 接收新曲线后从本地执行时间零开始，没有使用消息 `start_time` 对齐执行进度。

例如车辆已经达到可实现的最大速度，而参考仍更快，比例反馈再增大速度请求也无法让它追上。闭环不能消除执行能力不足。

### 1.4 建议修法，不是现有功能

先统一坐标系和数据时间，再把两个规划入口统一到一个起始状态策略：优先使用可靠、经过滤波的实际状态；仅在跟踪误差小且数据有效时考虑沿用参考导数。加速度需要合理估计或约束，不能把噪声速度直接差分后未经处理使用。

大幅不一致时应减速、重新初始化或停止，并记录失败原因。切到真实速度也应处理参考衔接及输出加速度，不能指望替换一个赋值就完成修复。具体阈值须通过底盘性能与闭环试验确定。

## 回答 2：里程计速度坐标系问题确实存在吗？

**接入符合标准、child_frame 为车体系的 Odometry 时，当前 FSM 存在速度坐标语义不匹配；但自带演示发布器又有另一处不规范，不能不检查数据源就一律旋转。**

### 2.1 标准并没有规定所有 pose 都在 map

已直接读取本机 `/opt/ros/humble/share/nav_msgs/msg/Odometry.msg`：pose 应在 `header.frame_id` 中表达，twist 应在 `child_frame_id` 中表达。

通常前者是 `map/odom/world`、后者是 `base_link/base_footprint`，但不是固定名称。正确修法应是“转换到规划坐标系”，不一定叫 map。

FSM 的 `odometryCallback()` 直接复制 twist；随后 `planGlobalTraj()`、`planGlobalTrajWaypoints()` 和起始状态函数把它当作与位置同坐标系的轨迹导数使用。中间没有速度旋转。

若父坐标系与规划系一致，车头 yaw 为 90°、车体系速度为 `(1,0,0)`，正确规划速度是 `(0,1,0)`；当前赋值得到 `(1,0,0)`，方向错误。但“车头不朝 +X 就一定错”太绝对：零速度不会出现方向差异，影响取决于实际姿态和速度。

### 2.2 为什么当前演示可能看不出问题？

| 发布端 | 实际写入 twist.linear 的数据 | 后果 |
| --- | --- | --- |
| [go2_kinematic_sim.cpp](../src/planner/plan_manage/src/go2_kinematic_sim.cpp) 的 `publishOdom()` | `vx_world_、vy_world_`，但 child_frame 默认是 `base` | 发布消息不符合其声明的 twist 坐标语义；FSM 直接复制却恰好得到所需世界速度 |
| [open_loop_controller.cpp](../src/planner/plan_manage/src/open_loop_controller.cpp) 的 `publishState()` | 世界参考曲线的导数 `vel`，child_frame 为机器人帧 | 同样存在语义不一致 |
| [PB ground_truth_adapter.py](../../meshnav_demo_ws/src/pb_vehicle_adapter/pb_vehicle_adapter/ground_truth_adapter.py) 的 `_publish_odom()` | 世界位置差分后经姿态逆旋转得到 `body_velocity` | twist 符合车体系语义，若原样接入当前 FSM 就需要转换 |

因此，如果只在 FSM 无条件新增旋转，原演示链路会把已经是世界系的数据再旋转一次。LIO 等其他数据源还需逐一检查，不能根据话题名称推断其实现。

### 2.3 具体修复顺序

1. 统一所有发布端遵守 Odometry 契约：父系 pose、子系 twist。两个演示发布器应将世界速度逆旋转到其所声明的子系。
2. FSM 收到消息后，把速度旋转到 pose 父系；若父系还不同于规划系，再把位置、姿态和速度统一转换到规划系。
3. 用同一消息时间的姿态/TF，先检查四元数有限性和有效范数，再归一化；缺少必要 TF 或数据过期时不能伪装为有效状态。
4. 所有使用 `odom_vel_` 的入口共享这个约定，避免某一路漏转换或转换两次。

当规划系就是 `header.frame_id`、参考点就是消息中子坐标系原点时，核心关系是：

```cpp
// 示意代码：前提是发布端已经遵守 twist 在 child_frame_id 中表达的契约。
// 使用当前消息的姿态；四元数有效性检查应在归一化前完成。
Eigen::Quaterniond q_parent_child(
    msg->pose.pose.orientation.w, msg->pose.pose.orientation.x,
    msg->pose.pose.orientation.y, msg->pose.pose.orientation.z);
q_parent_child.normalize();
Eigen::Vector3d v_child(msg->twist.twist.linear.x,
                       msg->twist.twist.linear.y,
                       msg->twist.twist.linear.z);
Eigen::Vector3d v_parent = q_parent_child * v_child;
// odom_vel_ = v_parent;  // 仅当 parent 与规划坐标系相同。
```

坡道上应使用完整三维姿态，不能只乘 yaw 旋转。若还要把速度参考点从雷达原点换到底盘原点，则需要考虑角速度与杆臂引起的线速度差；仅旋转解决的是同一物理点的表达坐标系问题。

此外，若 map→odom 随定位校正变化，要定义如何处理参考跳变，不能把离散定位修正当作真实底盘速度。

建议回归：水平 yaw=0°/90°/180°、侧移、带俯仰前进、静止、非单位/无效四元数，以及“演示链路”和“PB 标准里程计链路”。必须确认都只转换一次。本轮没有实施这些修改。

## 回答 3：为什么未来朝向不用当前里程计？全向底盘能否删掉朝向逻辑？

### 3.1 当前姿态与未来姿态不是同一个量

`estimateYawFromSegment(from,to)` 用 XY 路径切线估计该位置的车头方向；水平位移平方小于 `1e-8` 时才退回实测 yaw。这里不只是“向量严格为零”，还包括非常短的水平线段。

在终点/未来轨迹处查碰撞，需要未来车体朝向。当前里程计只告诉我们“此刻朝哪里”，不能自动代表几秒后的车头姿态。使用切线体现了“车头大致随路径转向”的假设。

当前闭环控制器的 `estimateDesiredYaw()` 确实根据前视轨迹方向（退化时参考速度）生成期望 yaw，并在误差较大时先转向。所以切线假设与现有控制策略有联系，不能说完全无依据；但控制器用的是前视方向，而碰撞检查常用短线段切线，两者也不严格相同，实际跟踪还有滞后。

### 3.2 全向允许方向解耦，但没有让姿态消失

全向机器人可以“车头朝东、向北侧移”。此时路径切线 yaw=90°，实际车头 yaw=0°。若碰撞模型是长条形，按切线旋转模型就会检查错误外廓，可能漏碰撞，也可能误报。

不能直接删除全部朝向逻辑，应区分：

| 用途 | 全向底盘如何处理 |
| --- | --- |
| 当前实测 yaw | 保留，用于定位姿态与实际车体碰撞 |
| 世界速度转机体系 | 保留；全向底盘也需要正确的 vx/vy 方向 |
| 期望 yaw 和角速度控制 | 明确策略：保持朝向、任务给定朝向或联合规划 yaw |
| “偏差过大先转向”及冻结 | 可重新设计，但须连同轨迹计时协议一起处理 |
| 未来碰撞朝向 | 用与执行策略一致的预测 yaw，并考虑跟踪误差 |

如果选择固定朝向，未来可以采用固定 yaw 参考，但还需处理当前姿态向该参考过渡的过程。若使用任意朝向下都覆盖车体的保守圆形包络，平面碰撞查询可不依赖 yaw；代价是窄通道可通过空间变小。

### 3.3 不止 FSM 这一处

必须一起检查：

- FSM 的终点调整、局部目标检查、未来轨迹安全检查。
- [bspline_optimizer.cpp](../src/planner/bspline_opt/src/bspline_optimizer.cpp) 的 `estimateSegmentYaw()`、`estimateControlPointYaw()` 及优化后的碰撞复查。
- [dyn_a_star.cpp](../src/planner/path_searching/src/dyn_a_star.cpp) 的起终点检查和邻居方向 `neighbor_yaw`。
- 控制器的期望 yaw、机体系变换与冻结反馈。

仅将 FSM 函数改成 `return getOdomYaw()`，会造成其他模块仍按路径方向检查，而且也没有正确描述未来会转向的情况。

## 回答 4：双圆柱是否不适合全向机器人？

**双圆柱是几何近似，全向是运动能力；两者并不互斥。是否适用取决于包络覆盖、姿态一致性和保守程度。**

### 4.1 这段代码实际上查了什么

[grid_map.h](../src/planner/plan_env/include/plan_env/grid_map.h) 的 `getInflateOccupancy(pos,yaw)`：

```text
heading = (cos(yaw), sin(yaw), 0)
front = pos + offset × heading
rear  = pos - offset × heading
分别查询 front/rear 在已膨胀占据缓存中的值
```

它没有现场对两个实体圆柱逐点遍历。圆柱半径与 Z 范围由 [grid_map.cpp](../src/planner/plan_env/src/grid_map.cpp) 的 `rebuildInflationOffsets()` 和 `updateInflationLayer()` 预先作用到障碍体素上；再查询两个中心是否落在膨胀障碍内。

XY 偏移使用半径内的离散网格点，Z 偏移从 `-inf_step_z_down` 到 `+inf_step_z_up`。所以这是体素化近似，不能直接等同连续几何精确碰撞检测。

### 4.2 它能否包住我们的车？

应以整车碰撞外廓为准，检查所有车体点是否都被两个圆柱的并集覆盖，并加入需要的误差余量。不能只比较车长和车宽。

例如两个水平圆心在 `(±d,0)`，半径为 r，车体中部侧边点 `(0,W/2)` 到最近圆心的距离为 `sqrt(d²+(W/2)²)`。即使 `r >= W/2`，也未必覆盖中部侧边，更不用说前后角点、突出装甲与云台。

若实际外廓不能被覆盖，模型会低估碰撞；若为了覆盖而把半径加得过大，又可能拒绝本来能通过的隧道。需要依据真实模型测量判断，源码没有提供 PB 整车包络覆盖证明。

### 4.3 全向和坡道分别带来什么问题

- **全向侧移**：双圆柱应跟随车头姿态旋转，而不是必然跟随速度方向；本质是回答 3 的姿态一致性问题。
- **原地旋转**：中心不移动，外廓仍可能扫到障碍，需检查旋转过程，不能只检查中心或平移路径。
- **坡道/顶棚**：当前查询只有 `pos + yaw`，没有按实际 roll/pitch 旋转整车体积。竖直膨胀不能完整表达车头抬起时前后端高度变化，必须专门验证净空。

上下膨胀还应按“障碍扩张”和“车体相对参考点范围”的反向关系理解：若障碍在 z_o，参考点落入 `[z_o-down, z_o+up]` 被判碰撞，对应障碍相对参考点落入 `[-up,+down]`。因此不能把 `z_up` 直接当车顶高度、`z_down` 直接当车底高度。

### 4.4 当前查询还有一个独立边界问题

地图外返回 `-1`，空闲通常为 0，被膨胀占据为 1。`getInflateOccupancy()` 在前圆柱查询结果非零时立即返回；若前方在地图外，会直接返回 -1，不再查后圆柱。

而终点调整函数使用 `if (final_occ <= 0) return true;`，会把 -1 作为无需调整而放行；其他调用处采用 bool 或 `!=0`，则会把 -1 当作非空闲。**这些调用对“未知/地图外”的处理不一致**。这和机器人是否全向无关，但不能忽略，也不能把该处返回 true 解释为终点已证实安全。

### 4.5 适合我们的选择

可以保留经过覆盖验证的双圆柱，并统一未来 yaw；也可以先用保守外接圆柱作为基线；若狭窄隧道和坡上净空要求高，则需要更贴近车体的多体积/有向包围盒模型及完整姿态处理。这是后续设计选项，当前代码尚未自动提供这些能力。

四个问题的共同点是：规划起始状态、未来车体姿态、碰撞包络和执行控制必须使用一致的物理与坐标语义。单独换一个速度来源、删除 yaw 或增大膨胀半径，都不足以完成整条链路的正确性修复。
