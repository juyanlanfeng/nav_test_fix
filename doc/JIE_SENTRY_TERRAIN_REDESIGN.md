# JIE 地形接触与碰撞判定分析：舵轮全向哨兵底盘改造方案

日期：2026-09-06。对象：当前 `/home/rainple/nav_test` 工作区，不是上游 JIE 的所有版本。

文档状态：**现状代码分析 + 待实施设计**。本文没有修改规划器、控制器、地图或机器人尺寸。文中“新增参数、模块、消息、测试”均为建议，不能当作当前已有功能直接启动。

## 1. 结论与改造范围

建议保留 JIE 的 ROS 接口、OctoMap 三维环境表示、GUI 和部分搜索基础设施，替换其“支撑 + 碰撞 + 可通行边”模型，并改造控制器和底盘接口。

推荐主线是：

```text
三维占据环境（保留坡面、隧道顶板、墙和未知空间）
    ↓ 提取、关联多个地面表面，保留上下层
地面层图（surface_id、地面高度、法向、粗糙度、净空、置信度）
    ↓ 使用真实轮位、接触模型、车体几何与运动能力
舵轮底盘状态/边可行性检测
    ↓ 搜索 (x, y, surface_id, yaw)，检查整段运动
带姿态、速度约束、地图版本的路径
    ↓ 全向轨迹跟踪 + 舵轮可执行性限制 + 安全监控
底盘速度命令 → 舵角/轮速执行 → 编码器、IMU、定位反馈
```

不能把改造简化为“降低机器人半径”“给占据体素统一放行几厘米”或“把 3D 图投影成单层平面图”。这些做法分别可能造成穿墙、穿低顶板、隧道上下层混淆。

用户说明 JIE 原用于机器狗。需要区分：**本仓库当前实现中没有足端位置、步态、落脚序列或机身姿态优化**；它是带局部支撑约束的三维体素路径搜索。不能把“在机器狗上使用过”等同于当前代码已经完整描述机器狗或舵轮底盘的越障能力。

### 1.1 当前已知与尚未知

已知：目标机器人是舵轮全向哨兵；需要处理缓坡、坡道接缝、隧道、多层路面及复杂场地；用户指出若干连接在真实机器人能力范围内。

尚未知：真实轮数与轮位、悬挂类型/行程、轮径、最小离地间隙、完整外廓、重心、舵角/轮速限制及实测纵横坡能力。本文不替这些数据编造数值。

当前 RMUC 的 `radius_xy=0.28 m`、`height=0.225 m` 和修改后的 Ceres 模型只是仿真代理配置，**不是哨兵真机参数**。保留它们可复现当前缺陷，但不能据此完成真机能力验收。

## 3. 当前代码究竟如何判断地形

### 3.1 地图语义：占据表面，不是经过完整观测的自由空间

当前 CAD 导入链路是：STEP → STL → 三角面/体素相交生成 PCD → OctoMap。PCD 表示被表面触及的体素中心，不是机器人应走的位置。

`pcd_to_octomap_node.cpp` 对保留体素执行：

```cpp
tree_->updateNode(tree_->keyToCoord(octo_key), true);
```

这里写入 occupied，没有像传感器射线插入那样证明中间所有空间为 free。`jie_path_node.cpp::isOccupiedCell()` 则按 `occupied_cells_` 查找；在边界内，不在集合中就返回 false。因此当前路径检测没有保留 unknown 和 observed-free 的区别。

这对于完整、经过校核的 CAD 静态场景是一种需要显式声明的假设；直接迁移到真实点云时不能将漏测区域当作无障碍。OctoMap 本身支持区分 occupied、free、unknown，问题在当前导入/查询链路的使用方式，而不是 OctoMap 无法表示。参见 [OctoMap 官方说明](https://octomap.github.io/)。

### 3.2 状态坐标：空体素中心，不是车体参考点

```cpp
index = floor(world_position / resolution);
world_center = (index + 0.5) * resolution;
```

当前节点是 `GridIndex{x,y,z}`。支持地面行驶时，候选节点位于支撑占据体素上方，但这不等于轮轴中心、底盘中心或 `base_link` 原点。

这也是改造时不能直接把当前路径 Z 当作真机 `base_link.z` 的原因。应明确区分地面接触高度、轮轴高度和车体参考高度。

### 3.3 支撑检测：附近有一个占据体素就可能满足

当前 RMUC 启动覆盖值：

| 参数 | 当前值 | 实际含义 |
|---|---:|---|
| `require_ground_support` | true | 必须找到支撑 |
| `strict_direct_ground_support` | false | 不限于正下方 |
| `ground_support_xy_radius_cells` | 1 | 搜索下方 3×3 水平邻域 |
| `ground_support_depth_cells` | 1 | 只搜索下方一层 |
| `resolution` | 0.04 m | 一层是 4 cm |

`groundSupportDepth()` 的语义可概括为：

```text
严格模式：候选正下方一层为 occupied → 返回 depth=1。
非严格模式：按深度由近到远，搜索 XY 邻域；遇到任意 occupied → 返回该深度。
没有找到 → 返回 -1，拒绝候选。
```

它不检查占据物是不是朝上的地面，不估计法向，不要求各个轮位都获得支撑，也不检查接触面积、悬挂行程、接触载荷和重心稳定性。边缘的一小块占据物甚至可能满足“存在支撑”的局部条件；后续碰撞检查可能再拒绝，但不能因此认为支撑检测本身已满足轮式底盘需求。

`rebuildDerivedLayers()` 使用 `groundSupportCandidateOffsets()` 从占据体素反向生成支撑候选，减少遍历量。这只是计算优化，没有引入新的物理支撑模型。

### 3.4 预封锁：基于邻域占据组合的几何规则

`rebuildPreblockedCells()` 从占据体素的同高度八邻域产生空候选，再应用两类主要条件：

1. 候选正下方有占据，并且同高度邻居的上方一层有占据 → 标为 preblocked。
2. 满足邻域空缺条件，候选正上方没有占据，正下方也没有占据 → 标为 preblocked。

第二类还受 `hasNonOccupiedNeighborSameLevel()` 等条件约束，具体以代码为准。外部人工编辑的禁行体素最终并入同一个集合。

这些规则没有直接使用米制坡度、轮径或真实越障高度，属于体素邻域启发式规则。分辨率改变时，其几何效果也随之改变。

`verticalColumnHasPreblockedGap()` 从候选下方向下检查：先遇到真实占据则结束并认为无预封锁间隙；先遇到 preblocked 则拒绝。这也不是轮胎接触或悬挂计算。

注意区分：

- `preblocked_cells_`：硬拒绝，可直接影响碰撞判定。
- `preblocked_costmap_`：邻近区域软代价，影响路径偏好。

把 `preblocked_costmap_weight` 调为 0，或者关闭软代价开关，**不会关闭硬预封锁检查**。正式改造还应把人工禁行与自动推导的风险分开，不能为了放行缓坡而同时删除用户禁行区域。

### 3.5 碰撞包络：默认旧半球，当前 RMUC 用竖直圆柱

`resolveRobotCollisionEnvelope()`：

- 新轴向参数均未设置时，保留旧的候选中心上半球检查。
- `robot_radius_xy` 或 `robot_height` 至少一个为正时，改用各向异性的竖直圆柱；未设的轴回退到旧半径。

当前 RMUC 为半径 0.28 m、支撑以上物理高度 0.225 m。它没有偏航相关矩形外廓，也不随地面法向倾斜。

设分辨率 `r`、支撑深度 `d`、高度 `h`，当前圆柱的体素偏移检查为：

```text
(dx*r)^2 + (dy*r)^2 <= radius_xy^2
min_dz = 1 - d
max_dz = floor(h/r) - d
```

RMUC `d=1`、`h=0.225`、`r=0.04`，所以候选相对高度检查 `dz=0..4`，水平半径为 7 个格子。代码以整数偏移和体素占据近似，不是连续实体与体素盒的精确相交检测；高度也存在量化误差，不能把配置值理解为毫米级净空保证。

`isCellTraversable()` 的检查顺序是：

```text
地图边界
 → 候选自身是否 occupied/preblocked
 → 是否找到支撑
 → 下方竖列是否存在预封锁间隙
 → 圆柱内是否出现 occupied/preblocked
 → 接受
```

关键代码：

```cpp
const GridIndex nearby_idx{idx.x + dx, idx.y + dy, idx.z + dz};
if (preblocked_cells_.find(nearby_idx) != preblocked_cells_.end()) {
  return false;
}
if (isOccupiedCell(nearby_idx)) {
  return false;
}
```

这里不会区分碰到的是墙、顶板、平台立面，还是轮胎应当贴合的缓坡地面。也没有离地间隙、轮胎与底盘不同几何、俯仰/横滚、舵轮转向外扫掠范围。

### 3.6 选点和搜索：位置可行不等于运动可行

`findNearestFreeCell()` 先测试原始点，否则按扩大的栅格壳层找到第一个可通行点。它不是按同一地面层/最近地表距离严格排序的吸附；多层场景需要防止吸到顶板或其他高度层。

`planAndPublish()` 在三维体素上使用 26 邻接 A*：

- 状态只有 XYZ，不含底盘 yaw、运动方向、舵角或速度。
- 邻居只调用 `isCellTraversable(nbr, ...)`；没有检验整个边段的扫掠碰撞和连续轮接触。
- 因而端点合法也不能证明对角运动不切角、不跨缝，或车体中途不碰撞。
- 高度每条边变化不超过一个体素只是离散邻接限制，**不是经过验证的爬坡/越阶能力**。
- 代价为格子单位欧氏距离加预封锁邻域代价，没有纵坡、横坡、轮速可行性、能耗或动态稳定代价。
- `lowest_traversable_only=false` 时可显示多高度候选，但没有稳定地面层身份及明确层间连接。

`publishPath()` 输出 `nav_msgs/Path`；普通路径点四元数为单位四元数，只有终点可能使用指定姿态。Z 是前述空体素中心，路径不包含底盘沿途真实 roll/pitch/yaw、限速、轮接触或地图版本。

另一个需要同步改造的生命周期问题：`tryPlan()` 普通失败只打印日志，没有统一发布失败结果并撤销上一条成功路径。地图更新时有清空逻辑，但不能用它替代所有规划失败的处理。新的导航任务应有独立 ID 和明确的旧路径处置策略。

## 5. 现有控制与仿真也需要适配

### 5.1 现有控制器具备横移输出，但不是舵轮控制器

`d1_controller.cpp` 当前跟踪计算可概括为：

```text
map 中的目标 XY 偏差 → 仅按机器人 yaw 旋转到局部平面
vx = clamp(kx * error_x)
vy = clamp(ky * error_y)              # enable_lateral_motion=true 时
wz = clamp(k_heading * heading_error + k_cross * error_y)
```

`lookupRobotPose2D()` 读取 TF 的 XYZ 和 yaw；路径目标推进及普通跟踪主要使用 XY，沿途没有同层判别、坡面速度约束或 roll/pitch 稳定性检查。

虽然有 `vy`，但 `wz` 仍随目标方向/横向偏差变化，不能自然保证“保持底盘朝向横移”。不要把 `enable_lateral_motion=true` 当作已经完成舵轮适配。

需注意的具体接口问题：

- `selectTrackingTarget()` 以 XY 容差推进点序；多层、绕行、急转处可能跳过关键接触/过渡状态。
- 普通跟踪使用 yaw-only 的平面变换，最终姿态阶段 `transformToBase()` 使用完整 TF；上坡时两阶段的速度坐标含义需要统一。
- 控制器未读取实时舵角、轮速和接触状态，也未约束模块转向速率及横纵向合成速度。
- 找不到 TF/目标的部分分支直接返回；空路径分支清空内部状态但未在那里显式发送零速。不能只依赖下游上一条命令自动失效。
- `require_start_command=true` 时每条新路径都进入等待确认；连续重规划需要重新设计任务状态机，不能让正常刷新变成反复停车等待。

`jie_twist_stamper` 仅复制 Twist、增加时间戳和 frame_id，**不做坐标转换、不做舵轮逆运动学、不做独立安全监控**。

### 5.2 RMUC 仿真是速度代理，不是完整舵轮动力学

[simulation_launch.py](../meshnav_demo_ws/src/mesh_navigation_tutorials/mesh_navigation_tutorials_sim/launch/simulation_launch.py) 对 RMUC 默认开启 `slope_aware_drive`；[ceres.urdf.xacro](../meshnav_demo_ws/src/mesh_navigation_tutorials/mesh_navigation_tutorials_sim/urdf/ceres.urdf.xacro) 条件加载 `SlopeAwareHolonomicDrive`，其他条件下才加载 DiffDrive。

该代理直接设置模型局部线速度 X/Y、角速度 Z，并保留其他分量的相关动力学状态；它有命令超时处理，但没有通过真实舵向关节、驱动电机、悬挂和轮胎摩擦完成舵轮运动。

因此：可以用来测任务接线和路径跟踪，不能据此证明真实轮胎能爬坡、不侧滑、不失去支撑。测试应分为“快速导航代理”与“真机参数动力学模型”两条，不能混用通过结论。

## 6. 目标地形模型：保留三维占据，增加多层支撑表面

### 6.1 环境占据与通行语义分离

OctoMap 保留完整占据障碍；额外建立局部/全局支撑表面图。每个 XY 位置允许有多个表面记录：

```text
surface_id（拓扑身份，不只是 Z 从低到高的排序号）
height / normal / roughness / uncertainty
terrain_class：ground、wall、ceiling、unknown 等
layer_neighbors：同层/坡道连接，不允许凭 XY 相邻跨楼层
clearance、边缘距离、地图修订号
```

顶板对于上层路径可能是支撑面，对于下层路径是车顶障碍；不能给整个 XY 柱统一打“可走/不可走”标签。

地面候选可结合 CAD 面信息、局部法向与连通关系提取；实际运行时结合点云、IMU、定位不确定度更新。局部拟合不能跨墙、台阶、隧道上下层一锅平滑。传感器缺失和地图截断处应携带 unknown/置信度，不能自动补成可通行地面。

可以借鉴高程融合的不确定度建模；例如 [ANYbotics elevation_mapping](https://github.com/anybotics/elevation_mapping) 显式考虑高程和位姿不确定度。它仅作为方法参考，不是这里要求直接安装的 Humble 多层导航替代品；其仓库也注明不再积极维护。

### 6.2 几何分辨率与误差预算

当前 4 cm 占据图足以暴露模型缺陷，但不应承担毫米级净空/接触判断。建议：

- 全局占据与粗搜索保留现有分辨率，避免全场盲目加密。
- 轮接触、坡道接缝、低顶板局部使用经过校核的细几何或细分辨率子图。
- 误差预算区分 CAD/点云误差、体素量化、定位/姿态误差、车体建模误差与动态变形。
- 上方占据带至少覆盖最高可行驶面 + 完整机器人高度 + 余量；不能照搬旧的 `z<=0.9 m` 截断作为真机全场保证。

不要通过删除所有底部若干层占据来消除离散化误差；这会同时删除低障碍和顶板边缘。

## 7. 舵轮底盘的状态可行性检测

### 7.1 输入机器人模型

使用实际轮数 N，不预设一定四轮。至少包含：

- 每个模块在底盘参考系中的安装位置、舵轴偏置、轮径、轮宽及完整转向包络。
- 悬挂/摆臂结构、行程、接触约束；如果是刚性无悬挂底盘，要明确允许何种接触组合和负载。
- 底盘、传感器、线束、云台在允许工作姿态下的完整碰撞几何。
- 最小离地间隙、质心及载荷变化范围。
- 实测纵向爬坡、横坡、台阶/沟缝、附着及制动能力，按速度和方向区分。

用近似平面拟合初估姿态可以作为数值初始化，不能替代刚体、悬挂和多轮接触求解。对于无悬挂四轮，四个任意地面高度一般不能同时满足一个刚体平面；必须显式处理离地轮和稳定性，而非强行拟合后宣称四轮接地。

### 7.2 轮地接触与车体碰撞分开

对状态 `(x,y,surface_id,yaw)`：

1. 在当前地面层上搜索各轮接触点，限制法向、局部粗糙度、接触面积与间隙。
2. 求满足轮径、安装几何及悬挂约束的车体 `z/roll/pitch`；无可行解则拒绝。
3. 检查实际接触集合和稳定裕量；准静态重心投影只能作为低速筛选，不能代替加速、转弯、坡上制动的动态稳定评估。
4. 按此姿态放置完整车体和模块几何，检测底盘、侧面、顶面与占据环境的碰撞。
5. 轮胎与被确认支撑面的接触仅在允许的接触区域和小误差范围内接受；不能将整个地面或整个车轮碰撞体从检测中移除。

缓坡上允许车轮接触，不表示底盘底板可以穿进坡面；坡顶要检查托底，坡脚要检查前后悬，隧道还要检查俯仰后最高点的顶板净空。

### 7.3 输出可解释结果，而不是只有 bool

建议接口（尚未实现）：

```cpp
StateEvaluation evaluateState(const TerrainState & state,
                              const RobotModel & robot,
                              const MapSnapshot & map);
EdgeEvaluation evaluateMotion(const TerrainState & from,
                              const MotionPrimitive & motion,
                              const RobotModel & robot,
                              const MapSnapshot & map);
```

结果应包含可行性、原因码、接触点、姿态、最小净空、风险/限速与命中的障碍位置。原因码至少区分：

`NO_SUPPORT`、`WRONG_SURFACE_LAYER`、`SUSPENSION_LIMIT`、`UNSTABLE_CONTACT`、`BODY_COLLISION`、`HEADROOM_LOW`、`EXCESSIVE_SLOPE`、`STEP_OR_GAP`、`STEERING_LIMIT`、`UNKNOWN_SPACE`。

这能让 GUI 直接指出“哪一个轮位缺支撑”“哪块顶板碰车”，不再只有 `A* planning failed`。

## 8. 搜索和边检查的改造

### 8.1 主方案：多层地面上的带航向搜索

推荐使用 `(x,y,surface_id,yaw)` 地面状态图；`z/roll/pitch` 由接触可行性解或局部候选姿态确定。若同一状态有多个会影响后续通行的接触/姿态解，要扩展状态或明确保留候选，不能随意只留一个最优局部解。

舵轮能够横移，不意味着可以忽略 yaw：矩形车体过窄口、云台外廓、轮位支撑和纵横坡稳定性都与朝向有关。运动原语应包括前后移、横移、斜移、原地转向及受限平移转向组合。

可以借鉴状态格与全向运动原语的组织方式。[Nav2 Smac State Lattice 官方说明](https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/planners_plugins/smac/smac_lattice/configuring_smac_lattice/) 给出了离线控制集和全向运动支持，但其现成平面规划器不自动解决本项目的多层接触、隧道及三维车体净空；本方案不要求直接换成 Nav2。

### 8.2 每条边验证运动全过程

必须沿运动原语检查连续接触和完整车体扫掠，不能只验证终点。检查：

- 是否沿合法地面连接，而非从顶板跳到下层。
- 所有关键轮轨迹上的支撑、台阶、沟缝和悬挂变化。
- 底盘转向扫掠、舵轮转角扫掠和坡道接缝处的托底/碰顶。
- 沿途俯仰/横滚变化、加速/制动约束及模块执行能力。

离散边采样须考虑平移步长、最大几何半径×转角引起的角点位移与地形尺度；自适应加密并加保守余量，不能只说“多采几个点”就等同连续无碰撞保证。需要时使用连续碰撞检测。

### 8.3 舵向具有历史状态

同一个底盘 pose 并不能唯一决定舵轮角度。为避免全局搜索维度爆炸，可采用两层策略：

- 全局层允许在经过验证的稳定位置停车重定向，计入转向时间，使用可实现的速度原语。
- 局部轨迹层读取当前模块舵角，对转向速率、加速度和换向进行时间参数化。

若某条狭窄坡道不能停车转向，就不能靠上述简化掩盖限制，需把相关舵向状态加入搜索或直接拒绝该过渡。

代价可包括距离、估计行驶时间、纵/横坡风险、粗糙度、稳定裕量、低净空、舵向变化与不确定性。真实碰撞、轮接触失效和超过实测能力必须是硬约束，不能用增加软代价代替。

## 9. 舵轮控制与哨兵朝向策略

### 9.1 解耦移动方向与底盘朝向

新的控制器显式跟踪平移轨迹与 yaw 轨迹：允许保持朝向横移，也允许按地形需要调整底盘朝向。哨兵云台瞄准方向与底盘导航 yaw 应分离；任务层的朝向偏好不能覆盖底盘碰撞和稳定约束。

明确 Twist 的参考点和坐标系：坡面切向速度、水平地图速度、倾斜 `base_link` 的 XY 速度不是同一个量。使用完整姿态/切平面映射，约定由哪层转换一次，不能只改 `frame_id` 字符串。

### 9.2 舵轮执行接口

如果下位机已经接收 `vx,vy,wz` 并完成舵轮控制，上位机应提供受限底盘速度并读取实际执行/限幅反馈，不重复下发模块逆解。若需在 ROS 内控制模块，再建立独立驱动层。

以理想平面刚体、模块安装点 `(x_i,y_i)`、轮径 `r_i` 为例，模块目标速度为：

```text
v_ix = vx - wz * y_i
v_iy = vy + wz * x_i
steer_i = atan2(v_iy, v_ix)
wheel_rate_i = hypot(v_ix, v_iy) / r_i
```

这是设计推导用的理想运动学，不是当前代码，也不是完整坡面轮胎模型。真实系统还要处理舵轴偏置、编码器零点、正反转等价解、舵角连续性、零速时保持舵角、速率/加速度上限、驱动转矩和饱和反馈。在非平面接触下需要按轮地切向方向处理，不能机械照搬同一水平速度给各轮。

### 9.3 安全与任务生命周期

新增统一的速度仲裁和停止通道。至少在以下情况停止或进入明确定义的降级状态：TF/定位超时、地图或路径版本不一致、无可执行新路径、舵向未到位、轮速/IMU 显示明显打滑、倾角超限、动态障碍侵入制动范围。

“发零速度”不等于坡上能够保持静止。下位机需要有经过验证的制动/驻坡能力及通信看门狗；丢失上位机命令时不得无限保持旧速度。

规划请求、结果、执行过程携带 `plan_id`、`map_revision`、`robot_profile_id`。失败时明确撤销或验证保留旧任务；不允许用上一次成功的 latched Path 冒充本次成功。

## 10. 数据接口与代码拆分建议

### 10.1 数据类型

| 数据 | 当前接口 | 改造建议 |
|---|---|---|
| 三维环境 | `octomap_msgs/Octomap` | 保留，明确未知空间策略；加入地图修订和来源元数据 |
| 支撑表面 | 无独立接口 | 内部多层图；调试用 PointCloud2/Marker，正式数据包含 surface_id、法向、误差 |
| 起终点 | `PointStamped`、`PoseStamped` | 用目标姿态/任务接口；实际导航起点来自时间一致的定位，人工起点仅用于离线规划 |
| 路径 | `nav_msgs/Path` | 保留用于可视化/兼容，但明确 pose 参考点；控制用新增带限速、层身份、版本的轨迹消息/Action |
| 路径 Z/姿态 | 空格中心、沿途单位四元数 | 改为明确定义的底盘参考位姿；同步升级消费者，避免把旧路径误解为新语义 |
| 速度 | Twist → TwistStamped | 约定坐标与参考点，接入仲裁、超时及底盘反馈 |
| 失败信息 | 日志 + 无新路径 | 显式状态/Action result、原因码、失败位置和受影响轮/车体部件 |

不能把速度上限塞进 `Pose.position.z` 或四元数等无关字段；新增消息必须定义单位、时间语义、坐标系和版本兼容。

### 10.2 推荐模块边界（均待新增）

| 模块/文件建议 | 输入 → 输出 | 与当前代码关系 |
|---|---|---|
| `terrain_surface_map.*` | 占据/局部几何 → 多层表面及邻接 | 独立于机器人尺寸，避免每次改底盘重做 CAD 转换 |
| `sentry_robot_model.*` | 真机 profile → 轮位、悬挂、外廓、约束 | 替代只用半径/高度表达所有几何 |
| `wheel_contact_evaluator.*` | 状态+表面 → 接触集合、可行姿态 | 替代把 `groundSupportDepth()` 当作整车支撑判据 |
| `terrain_collision_checker.*` | 姿态+接触+三维环境 → 碰撞/净空 | 舵轮模式替代 `isCellTraversable()` 的统一圆柱检查 |
| `terrain_motion_validator.*` | 状态+原语 → 边可行性与限制 | 补齐当前 A* 缺少的运动过程检查 |
| `sentry_terrain_planner.*` | 状态图+任务 → 带 yaw 的路线 | 复用搜索思想；不把所有新逻辑继续堆进单个 ROS 节点 |
| `sentry_trajectory_controller.*` | 路线+定位+模块状态 → 有约束底盘命令 | 替换当前 XY 追点式控制作为正式执行层 |
| 独立安全监控/仲裁节点 | 状态健康度+命令 → 获准速度/停止 | 两套导航共用，确保只有一个速度执行源 |

建议增加模式开关，例如 `traversability_model=legacy|sentry_wheeled`。这是**新设计名，当前没有此参数**。旧模式及既有测试保留；新模式不要继续复用无法解释的自动硬预封锁逻辑，但人工禁行应作为独立硬约束保留。

缓存键至少包含地图修订、机器人配置版本、层、位置和 yaw；底盘尺寸、姿态外廓或地图变化后必须失效。先离线预计算静态场地、局部增量更新，再依据实际性能决定是否需要分层搜索。

## 11. 分阶段实施与验收

| 阶段 | 工作 | 必须达到的出口条件 |
|---|---|---|
| P0：冻结基线和真机规格 | 保存现有地图/日志/参数；整理 CAD 与实测能力；加入结构化失败报告和路径失效处理 | 能稳定复现当前失败；每次失败可定位到规则和几何；未知真机参数显式报缺失 |
| P1：支撑与碰撞内核 | 提取多层地面；实现真实轮接触和随地形姿态的车体碰撞；先做离线状态/边检测 | 1.5° 连续缓坡不再出现量化禁行带；真实低障碍、墙、低顶板仍拒绝；不改原地图消除障碍 |
| P2：带 yaw 的全局路径 | 多层状态搜索、同层吸附、边扫掠检测、轨迹/状态消息 | 两个当前选点在经验证的能力范围内可连通；路径每条边均通过姿态/接触/碰撞检查 |
| P3：全向执行与模块约束 | 平移/yaw 解耦、速度时间参数化、驱动反馈、停止仲裁；建立真实舵轮动力学模型 | 横移不被迫朝目标转头；模块转向速率和轮速不超限；失败/超时按规定停车；坡上行为通过动力学测试 |
| P4：实测闭环 | 受控场地低速开始，逐步测试坡道、横坡、隧道、接缝与干扰 | 有实测误差、接触、滑移、制动和安全记录；参数由数据确认后才扩大任务范围 |

P1 不是“能在 GUI 画出线就可以上车”；P2 不是“代理仿真走过一次就代表真机能过”。各阶段需要同时验收正例和应拒绝的反例。

### 11.1 必补的回归测试

| 测试 | 期望 |
|---|---|
| 1.5° 连续缓坡横跨多个体素高度边界 | 能力范围内连续通行，不出现随体素层变化的隔离带 |
| 平移体素原点、改变合理分辨率 | 不因半格偏移产生结论翻转；临界处显式体现误差和余量 |
| 两个本次实测点及其代表性断点 | 回归记录状态/边失败原因；改造后用完整车体检验，不用点足迹冒充 |
| 墙、薄立板、矮凸起、窄缝 | 不得因“允许轮地接触”而穿越 |
| 隧道上下两层、坡道层间连接 | 同 XY 保留不同 surface_id，不能跳层；上下层均独立验收 |
| 隧道高度临界及俯仰过入口 | 依据完整外廓/误差拒绝碰顶，不能只比较竖直标称高度 |
| 坡顶/坡脚/短接缝 | 检查前后悬、托底及悬挂，不只检查坡面法向 |
| 轮位位于悬崖、沟缝、三点/四点非共面支撑 | 按真实结构和稳定约束接受/拒绝，禁止任一孤立占据点代替整车支撑 |
| 对角切角、原地旋转、横移过窄口 | 整段车体和模块扫掠合法 |
| 坡上横移、转向、制动 | 不超过方向相关能力，滑移/稳定性由动力学与实测验证 |
| 地图更新、规划失败、TF 失效、通信断开 | 不继续执行失效路径；底盘看门狗/制动响应可测 |
| Mesh/JIE 切换 | 始终只有一个获准速度源，旧任务不得复活 |

已有 `test_robot_collision_envelope.cpp` 继续验证 legacy 行为；新建轮接触、地形碰撞、层间连接、运动边与任务生命周期测试。场地图验证脚本应同时报告几何一致性、全局连通性与真实机器人可行性，三者不是同一项。

### 11.2 验收记录必须含什么

地图/机器人配置哈希、起终姿态和层、定位误差、最小净空、接触失效次数、最大纵横倾角、轮速/舵速饱和、路径跟踪误差、规划耗时、重规划行为、故障到停止的延迟与制动距离。

阈值根据实测能力和任务风险设定；本方案不虚构“允许 55°坡”或固定停止距离。旧 Mesh 构图中的 55°是为了保留 CAD 短过渡几何，不是哨兵持续爬坡能力。

## 12. 开始正式改造前需要提供的真机资料

以下信息可以用 CAD、标注尺寸图、控制接口文档和实测记录提供，不要求一次全部手工填写。

| 必要资料 | 影响哪些设计 |
|---|---|
| 模块数量、安装坐标、舵轴偏置、轮径/轮宽 | 接触位置、逆运动学、转向外廓 |
| 完整机器人长宽高、最低底板/前后悬、云台运动外廓 | 碰撞、窄口、托底、隧道净空 |
| 悬挂/摇臂结构与行程，是否允许某轮短时离地 | 接触可行性和姿态求解 |
| 质量、重心及载荷变化 | 稳定性、加速、制动 |
| 已测纵坡、横坡、台阶、沟缝及对应方向/速度 | 地形硬约束与限速，而不是统一坡度阈值 |
| 舵角范围/速率、轮速/加速度/转矩、反馈频率 | 运动原语和局部执行 |
| 下位机接收 Twist 还是模块命令；速度坐标和参考点 | 驱动分层、TF 约定、避免重复逆解 |
| IMU、里程计、定位、雷达配置及误差 | 状态估计、地图不确定度与安全降级 |
| 停车/驻坡、急停、失联处理机制 | 真机安全闭环 |

在这些信息补齐前，可以先实施 P0 和不依赖具体能力数值的接口/诊断/几何单元测试；依赖能力的测试使用明确标注的测试模型，不把测试值写成正式哨兵配置。
