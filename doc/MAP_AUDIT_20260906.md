## 发现的问题与修改

1. 旧 PCD 先 `round(surface/pitch)`，再输出 `(key+0.5)*pitch`，
   会把部分表面移到旁边的体素。新版按真实体素边界做相交检测，不再引入这半格偏移。
2. 有限三角细分的采样点不保证覆盖所有边缘格。新版用分离轴定理判断
   三角形与体素立方体是否相交，既不会漏掉薄边缘，也不会把整个三角形包围盒填实。
3. 旧显示节点把 OctoMap 合并后的大体素画成一个最小方块，造成假裂缝。
   已修为展开所有被覆盖的小体素；实际 ROS marker 与 PCD 的体素集合逐格一致。
4. 旧网格哈希对新版 631,564 个坐标仅产生 1,024 个哈希值，导致严重查询退化。
   已改用充分混合的整数哈希；坐标相等判断、机器人包络和规划规则不变。

实际多进程验证运行了转换器、显示节点、JIE 规划器，使用独立 ROS 域，没有驱动
Gazebo 机器人。修复前后都完成了同图回归，生成层数量和两侧路径结果相同。
Field 20 项单测通过，碰撞包络及 C++ 格式检查通过；相关节点已构建。

选择 4 cm 而非继续用旧 5 cm，是为了在修正真实坐标之后仍能表达约 0.246 m
隧道净空与 0.225 m 规划高度。离散地图仍有体素误差，不能把“能规划通过”视为
带姿态、悬挂和动力学的实车通行验证。

新版从完整 visual STL 生成，不再受碰撞网格 500k 面预算影响。相较同分辨率的
collision STL 图，额外保留了 6,898 个较高表面体素（其格下界均不低于 0.36 m）。
这些 CAD 表面仍作为障碍保留；Gazebo 精简碰撞网格的高处碰撞细节可能更少。

## 使用新版

关闭旧 JIE 导入 launch，再启动。已打开窗口的 `_working_cloud` 是内存副本，
仅替换磁盘文件不会刷新它；旧导出的 OctoMap 地图包也不会自动更新。
每个用于本次仿真的终端都应使用相同 ROS 域及 DDS 配置：

```bash
source /opt/ros/humble/setup.bash
source /home/rainple/nav_test/meshnav_demo_ws/install/setup.bash
source /home/rainple/nav_test/jie_3d_nav/install/setup.bash
export ROS_DOMAIN_ID=42
export ROS_LOCALHOST_ONLY=1
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export CYCLONEDDS_URI='<CycloneDDS><Domain Id="any"><Discovery><ParticipantIndex>auto</ParticipantIndex><MaxAutoParticipantIndex>100</MaxAutoParticipantIndex></Discovery></Domain></CycloneDDS>'

ros2 launch jie_octomap import_pcd_map.launch.py \
  use_sim_time:=true rmuc2026_profile:=true start_import_gui:=true
```

窗口里重新选择：

```text
/home/rainple/nav_test/field/converted_rmuc2026/jie_nav/rmuc2026_field.pcd
```

分辨率应为 **0.040**，预降采样 **0**。先显示点云，再点击“转换为 Octomap”。
本机本轮就绪约 22 秒，实际以 `Preblocked costmap rebuilt` 为准。
生成派生层之后再选起终点；颜色中的“占据”也包括支撑地面，不能把所有橙色体素
都理解成挡住车子的障碍墙。
