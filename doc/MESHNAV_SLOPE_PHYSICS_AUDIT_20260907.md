# MeshNav 短斜坡卡住：物理仿真排查

日期：2026-09-07。范围：RMUC2026 场地隧道旁短坡，暂停 DDDMR 工作。本次没有修改生产地图、机器人尺寸、摩擦系数或导航参数。

## 结论与边界

已在独立 Gazebo 物理仿真中复现一种明确的卡住机制：**机器人偏向坡道一侧进入时，右侧车轮与相邻高处结构接触，持续给速度也不能向前；向通道内侧平移进入位置后，同一模型能够上坡。**

这不是“所有短坡都爬不上去”，也不能仅靠全局路径成功来判断实体一定能通过。尚未回放用户当时的完整导航轨迹，因此不能断言用户遇到的每一次停滞都由同一原因造成。

## 实际对照实验

坐标为当前场地世界坐标，单位 m。初始 x=-0.5、z=0.015；先静置 1 秒，再以 0.2 m/s 发出开环速度，最后停止指令并观察 2 秒。yaw 单位为度；速度按初始姿态换算为机器人坐标，使初始行进方向为世界 +X。没有运行 MeshNav 控制器。

## 为什么规划通过，实体却可能卡住

当前小车不是经过实机标定的舵轮动力学模型：

- `meshnav_demo_ws/src/mesh_navigation_tutorials/mesh_navigation_tutorials_sim/urdf/ceres.urdf.xacro` 定义车体和驱动插件。本次沿用 RMUC 参数：轮半径 0.10，车体长宽高 0.32 × 0.26 × 0.10。
- 同目录 `wheel.urdf.xacro` 使用固定朝向的圆柱轮和滚动关节，没有舵向关节。轮子外缘总宽约 0.49 m，不能用车身宽 0.26 m 代替整车占用宽度。
- `meshnav_demo_ws/src/mesh_navigation_tutorials/mesh_navigation_tutorials_sim/src/slope_aware_holonomic_drive.cpp` 直接设置车体平面速度和偏航角速度，并保留垂向速度与横滚、俯仰角速度；这是简化全向驱动，不是轮电机扭矩及转向闭环。
- `meshnav_demo_ws/src/mesh_navigation/mesh_controller/src/mesh_controller.cpp` 从网格路径/向量场生成控制速度。规划中心点落在可通行面上，不等于带姿态变化的所有轮子和车身都有净空。

因此应分别检查“地形可通行”“整车扫掠体无碰撞”“控制器实际跟踪轨迹”。本次中心位置横移成功，不能把固定朝向车轮直接认定为此次卡住的唯一原因。也不能在未测量的情况下把问题归结为摩擦力或驱动扭矩不足。

另外，里程计插件配置为二维不等于导航完全丢失三维姿态；`ground_truth_localization.cpp` 会用仿真真实姿态与 odom→base 的逆变换计算 map→odom，检查 TF 时应看完整链路。

## 如何复现

在项目根目录执行：

```bash
cd /home/rainple/nav_test
source /opt/ros/humble/setup.bash
source meshnav_demo_ws/install/setup.bash
python3 field/probe_slope_physics.py --y 5.72 --seconds 5
python3 field/probe_slope_physics.py --y 5.80 --seconds 9
python3 field/probe_slope_physics.py --y 5.95 --yaw 90 --seconds 9
```

两个 `source` 分别加载 ROS/xacro 和本工作空间插件环境。Python 脚本展开当前机器人配置，读取当前场地碰撞模型，构建独立的物理测试世界，并编译 `field/slope_probe_drive.cpp` 后运行；需要现有 Gazebo 6 开发库、g++ 和 pkg-config，不会自动安装包。

每次使用独立 `IGN_PARTITION`，不会向其他仿真实例发运动命令。为了减小资源占用，不启动 GUI、导航器、ROS 桥或 GPU 传感器，去掉视觉元素和传感器但保留碰撞几何、惯量和关节。使用的全向驱动插件来自已构建的工作空间；若之后修改插件源码，需要重新编译才能测试修改版。

程序数据流：

```text
当前 xacro + 场地碰撞 STL → 独立 SDF 世界 → Gazebo 物理引擎
诊断客户端 → ignition.msgs.Twist → 当前全向驱动插件
真实模型姿态 → ignition.msgs.Pose_V → poses.csv
物理接触组件 → 接触位置/碰撞体名称 → stderr.log
```

程序结束码 0 表示测试时长执行完毕，**不表示爬坡成功**；须根据位置轨迹确认是否达到平台。新运行会保存 `arguments.json`；上表较早的实验目录没有该文件，可结合表格和保存的 SDF 确认初始条件。生成物位于地图生成目录中，不应当作已纳入 Git 的回归数据。

## 下一步修复方向

1. 先在实际导航运行中记录速度指令、真实姿态和接触，确认是否走到了上述偏侧区域。如果控制器已经输出零速度，应另查控制器退出状态，不能套用“持续给速度仍被碰撞阻止”的结论。
2. 对短坡入口加入完整轮组/车体的三维净空及姿态扫掠检查，进入坡前居中并稳定航向；不是简单将路径点投影到坡面，也不是全局放宽障碍阈值。
3. 将接触位置对应回原始 STEP，确认邻侧几何是否真实存在。只有证明是转换伪影，才局部修正碰撞网格；不要直接删除所有坡边碰撞。
4. 用实际机器人外廓、轮距、轴距、离地间隙及越障能力校准模型。当前没有完整实机参数，不为“能通过”而随意缩小车辆或提高摩擦系数。

本次完成的是可重复的故障定位，不是已完成导航闭环修复或实机通过认证。保留了用户已有修改，生产地图和导航行为未被更改。

## 具体修复方案（待实施，不是已生效的配置）

推荐顺序：**补齐观测 → 实现窄坡入口约束 → 加入整车碰撞校验 → 按实机校准动力学**。先解决已经复现的偏侧接触，不同时改地图、车体尺寸、摩擦和控制器，否则无法判断是哪项改动有效。

### 第一阶段：记录实际导航失败，确定应改哪一层

保持现有仿真和 MeshNav 启动方式，另开终端执行：

```bash
cd /home/rainple/nav_test
source /opt/ros/humble/setup.bash
source meshnav_demo_ws/install/setup.bash
ros2 topic info /cmd_vel --verbose
ros2 topic info /tf_gt --verbose
ros2 bag record /cmd_vel /tf_gt /tf /tf_static /clock
```

`topic info` 用于核对实际类型、发布者和 QoS；记录终端必须与仿真使用相同的 `ROS_DOMAIN_ID`。当前桥配置的 `/cmd_vel` 是 `geometry_msgs/msg/TwistStamped`，`/tf_gt` 是仿真真实位姿的 TF 消息；不要按普通 `Twist` 随意发送测试指令。`bag record` 只录制上述小范围话题，不录点云，以节省空间。复现一次后按 Ctrl+C 停止，保留自动生成目录。ROS bag 不包含物理接触，接触仍需用前述独立测试或把接触观测接入实际仿真。

判别依据：

| 观测 | 下一步 |
| --- | --- |
| 实际速度指令持续非零，但真实位置不动，同时出现邻侧接触 | 执行第二、三阶段 |
| 控制器返回 `OUT_OF_MAP` 或已输出零速度 | 检查 `computeVelocityCommands()` 的面搜索、TF 时间和三维表面归属，不改摩擦 |
| ROS 指令存在但没有到达 Gazebo | 检查桥、话题类型和驱动订阅，不改地图 |
| 无侧面碰撞，轮/车体动力学仍无法推动 | 在第四阶段单独标定驱动模型 |

建议在 `mesh_controller/src/mesh_controller.cpp` 的面搜索失败和向量场读取失败处补充节流日志：原始 pose、投影后位置、当前面编号、输出速度及失败原因。保留原始三维 pose 给后续碰撞检测；当前函数会将 `robot_pos_` 投影到地形表面，不能用它代替真实车体位置。

### 第二阶段：最小可行修复——入坡前居中，上坡时限制偏侧和转向

这是新增功能，**不能只改现有某一个 YAML 数字完成**。实现位置：

| 文件（相对项目根目录） | 拟修改内容 |
| --- | --- |
| `meshnav_demo_ws/src/mesh_navigation/mesh_controller/include/mesh_controller/mesh_controller.h` | 增加通道配置、状态机、航向/横向误差、停滞检测状态 |
| 同包 `src/mesh_controller.cpp` | 在 `computeVelocityCommands()` 得到常规速度之后、最终赋值输出之前执行通道约束；在 `setPlan()`/`cancel()` 重置状态 |
| `meshnav_demo_ws/src/mesh_navigation_tutorials/mesh_navigation_tutorials/config/rmuc_ramp_corridors.yaml`（拟新增） | 保存经过测量的坡道入口、出口、通道边界、方向和局部限速 |
| 同教程包 `launch/mbf_mesh_navigation_server_launch.py` | 向控制器加载新增配置；具体参数前缀沿用当前控制器实例命名 |

每个通道至少包含 `frame_id`、入口/出口中心、有效地形层或高度范围、左右边界及允许航向，不能只用一个 XY 矩形，否则会把隧道顶面与底面混为同一通道。

本次测试的 y=5.95 可作为这个短坡的**初始中心线候选**，入口应选在 x=-0.5 之前可安全调整姿态的低平台，出口选在 x≈0.8 之后的高平台。入口、出口具体位置和边界须先在碰撞模型上验证，不能把这些近似坐标直接复制到其他坡道。

控制逻辑：

1. **接近**：只在当前计划确实穿越该通道、且机器人位于正确地形层时触发。检查入口调整区足够容纳整车。
2. **对齐**：在低平台先居中、再对齐通道方向。不要一边贴近坡边上坡一边大幅转向。初始测试条件可设横向误差小于 0.02 m、航向误差小于 5°，持续 0.3 s 后才开始进入；这些是待验证阈值，不是实机精度结论。
3. **通过**：初始限速 0.10 m/s；用通道方向前进，以受限横向修正保持居中。全向底盘仍保留横移能力，但不再无条件执行可能指向侧边的网格向量场。下坡时按行驶方向重新定义前进轴。
4. **退出**：整车尾部离开坡段且姿态稳定后，恢复常规 MeshController。不能仅以机器人中心越过出口作为退出条件。
5. **异常**：若持续 2 s 指令速度大于 0.05 m/s，而真实沿通道位移小于 0.02 m，输出零速并报告停滞。这只是初始检测阈值，需根据仿真噪声调节。不要自动持续顶撞或未经后方净空检查倒车。

在通道切平面中计算横向误差 e 和航向误差 ψ，示意控制为 `v_forward=v_limit`、`v_lateral=clamp(-k_y*e)`、`w=clamp(-k_psi*ψ)`；再变换到车体坐标，并做加速度限制。增益和限幅由低速测试确定，不将世界坐标速度直接写入车体 `linear.x/y`。进入前对齐、通过时小幅修正是不同阶段。

仅在 RViz 手动增加中间目标可做临时人工验证，不能替代上述约束：当前 `setPlan()` 复制网格向量场，`computeVelocityCommands()` 主要读取当前位置的向量方向，并不保证严格逐点跟踪人为画出的中心线。

### 第三阶段：可靠修复——用完整车体和轮组判断通道净空

当前 RMUC 静态参数在 `mesh_navigation_tutorials_launch.py` 中为 `static_inscribed_radius=0.28`、`static_inflation_radius=0.3`。它们并不等于三维扫掠碰撞检查。车轮外缘宽约 0.49 m，而不是车体宽 0.26 m。

短期可做保守几何预检：沿通道方向固定车身时，最低通道宽度应覆盖整车投影宽度及两侧裕量，例如水平状态 `0.49 + 2×0.03 = 0.55 m`。3 cm 只是待验证的初始裕量。斜向通过、横滚和俯仰时必须重新计算投影和三维净空，不能一直套用 0.55 m。

对于约 0.48 × 0.49 m 的水平包围矩形，保守外接圆半径约为 0.343 m；直接把所有膨胀半径都改成这个值还可能堵死本来可按特定方向通过的窄道。因此**不推荐全局放大/缩小膨胀作为最终修复**，更不能降低高度差阈值约束来“强行放行”。

建议新增独立的通道校验工具（拟命名 `field/check_ramp_clearance.py`）：

- 输入当前展开后的机器人碰撞几何、当前场地碰撞 STL、通道中心轨迹和候选姿态；统一使用当前转换记录的米制坐标，不能直接把 STEP 的原始坐标混入。
- 沿轨迹采样，并对相邻采样姿态做连续/自适应碰撞校验。初始采样间距可用 0.01 m、角度变化上限 1°，再减半验证结果稳定；离散采样本身不是无碰撞证明。
- 根据轮组支撑面推算车身高度、俯仰和横滚，测试邻近姿态扰动。车轮与支撑坡面的正常接触允许存在，但侧壁、顶棚与车身穿透应判失败；不能把所有接触都判为障碍，也不能豁免整个车轮碰撞。
- 输出最小净空、失败的碰撞体对和世界坐标；生成 RViz `MarkerArray`，显示整车轮廓、中心线、左右边界及危险接触点。
- 对确认可行的通道生成“方向及姿态受限的可通行连接”；全局规划使用该连接，局部控制执行第二阶段状态机。第一版可先做离线通道校验，但必须说明它不能防范运行时动态障碍。

只有碰撞点回查原始 STEP 后确认存在转换伪影，才修改 `field/build_component_collision_mesh.py` 对应的转换处理并生成**新文件名**的碰撞网格进行对照。保留旧网格，检查入口、坡面、侧壁和顶棚全部截面；不要通过删除隧道顶部、侧面或地板来让测试通过。若修改地形几何，还必须同步验证导航网格与碰撞网格坐标及表面一致性。

### 第四阶段：机器人模型按实机校准，而不是为过坡缩小

需要补齐的实机数据：总长宽高（含外伸部件）、轮半径/宽度、轮距和轴距、最低离地间隙、质量与重心、最大坡度、可越台阶高度，以及舵轮转向速度/驱动限制。没有数据时保持当前模型，不宣称已代表实际哨兵。

修改位置为 `ceres.urdf.xacro`、`wheel.urdf.xacro` 和仿真 launch 中的尺寸参数；同步更新导航高度和占用轮廓。只改 RViz visual 不会改变物理碰撞，修改 collision 后也应一致更新惯量与关节安装位置。

若目标是验证真实舵轮通过能力，后续应将 `slope_aware_holonomic_drive.cpp` 的车体速度覆盖方式替换为舵向关节和轮驱动闭环。对位于底盘 `(x_i,y_i)` 的轮，目标速度分量为 `(vx-wz*y_i, vy+wz*x_i)`，由此求舵角与轮速，再加入转向限速、轮速/扭矩限制和实机参数。届时禁用原车体速度覆盖插件，避免两套驱动争用。这个动力学改造不是修复当前偏侧碰撞的前置条件，应另行验收。
